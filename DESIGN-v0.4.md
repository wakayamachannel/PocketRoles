## A. Lobby timer, auto-start, extension, 廃村 — `src/Lobby/LobbyTimer.cs` + `src/Lobby/AutoStart.cs` (owner: lobby)
Facts: the client has no timer field. The server sends RPC 60 `LobbyTimeExpiring` (packed secondsRemaining, bool extensionAvailable[, packed hostId, packed extensionId, packed extensionSeconds]) → `LobbyBehaviour.HandleLobbyTimerExtensionRequest(int timeRemainingSeconds, bool isExtensionAvailable, int hostId, int extensionId, int extendedTimeSeconds)`; the host extends with `LobbyBehaviour.RpcExtendLobbyTimer()` after setting `currentExtensionId` (RPC 61, packed extensionId). Vanilla HUD: `HudManager.Instance.ShowLobbyTimer(int)`, `LobbyTimerExtensionUI.timerText.GetSecondsRemaining()`, `OnLobbyTimerExtended()`. Official lobbies last ~600 s (EHR shows `ShowLobbyTimer(597)` at lobby start).
* `LobbyTimer`: on `GameStartManager.Start` postfix (online, host) start an estimate `Deadline = realtime + 597`; `LobbyBehaviour.HandleLobbyTimerExtensionRequest` postfix overrides `Deadline = realtime + timeRemainingSeconds` and records `(isExtensionAvailable, hostId, extensionId)`; `LobbyBehaviour.LobbyTimerExtended` postfix (or `HudManager.OnLobbyTimerExtended`) → `Deadline += extendedTimeSeconds`, clear the offer. `Remaining` (int seconds) public. Display: call `HudManager.Instance.ShowLobbyTimer((int)Remaining)` once at lobby start so the vanilla timer widget is visible, and append "ロビー残り mm:ss" to the PingTracker line (host). `/time` → chat reply with the remaining time (all players). Notices to everyone at 120 s and 60 s (once each).
* `Extend()`: if an offer is pending for us → `LobbyBehaviour.Instance.currentExtensionId = extensionId; RpcExtendLobbyTimer(); HudManager.Instance.LobbyTimerExtensionUI.HideAll();` return true; else return false (no offer yet — the server only offers near the end; if `Remaining < 90` and no offer exists fall back to 廃村).
* `AutoStart` state machine (ticked from `HudManager.Update` postfix while in the lobby, host, `Options.AutoStart`): per `DESIGN-v0.4 §A2` below. Force start = `gsm.startState = GameStartManager.StartingStates.Countdown; gsm.countDownTimer = seconds;` (vanilla Update then counts down, broadcasts SetStartCounter and calls FinallyBegin); `MinPlayers` is set to 1 in a `GameStartManager.Update` **prefix** only while `Options.AutoStart || Game.TestMode || HaisonPending`.
* 廃村 (`Haison.Run()`): set `HaisonPending = true`, notify, force start with a 5-s countdown; when the game starts, in `IntroCutscene.OnDestroy` postfix (or 1 s after `GameManager.Instance.GameHasStarted` when no intro instance appears) → `GameManager.Instance.ShouldCheckForGameEnd = false; ShipStatus.Instance.enabled = false; GameManager.Instance.RpcEndGame(GameOverReason.ImpostorDisconnect, false);` — role assignment must be skipped for a haison game (`RoleAssignment` checks `Haison.Active` and dispatches nothing; `WinConditions` ignores it; no summary chat). Everyone returns to the same lobby with a fresh timer; reset state.
* Hotkey F7 (twice within 3 s) during a game: `WinConditions.EndGame` is NOT used; do the same immediate end as 廃村 with `GameOverReason.ImpostorDisconnect` after a host notice "ホストが試合を終了しました（廃村）". `/haison` command = same.

### A2. Auto-start rules
Options `[Lobby] AutoStart=false, AutoStartPlayers=10 (4..15), AutoStartCountdown=5, TimerWarnAt=60, ExtendNoticeDelay=5`. Commands `/autostart on|off|<N>`, `/start` (force start now, any count), `/cancel`.
Player-facing texts must explain the mechanism (random players otherwise think the room is closing): 廃村 notice = "ロビーの時間切れを防ぐため、一度ゲームを開始してすぐ終了します。部屋はそのまま続き、コードも同じです。退出せずにお待ちください。" (+zh/en); after returning: "ロビーを更新しました。そのまま遊べます。". Extension notice: "ロビーの時間を延長します（部屋はそのままです）".

1. count ≥ AutoStartPlayers and idle → notice "{count}人揃いました。{n}秒後に開始します" → countdown (host HUD text) → force start. During the countdown, if count < AutoStartPlayers → cancel (`gsm.ResetStartState()`), notice, back to idle.
2. Remaining ≤ TimerWarnAt: if count ≥ AutoStartPlayers → 5-s start; else notice "ロビーの残り時間が少ないので{k}秒後に延長します" → after k s **always** `Extend()` else 廃村 (never cancelled by players leaving).
3. Otherwise idle; rule 1 fires as soon as the count is reached.

## K. Chat translation (owner: translate; follow-up after the v0.3/v0.4 workflow) — `src/Chat/Translator.cs`
Requested 2026-09-07: foreign-language chat should appear translated into Japanese for the host (and optionally for everyone), and the host's Japanese can be translated for foreign players.
* Options `[Translate] Enabled=false`, `Provider=google|deepl|none` (default google = the public `translate.googleapis.com/translate_a/single?client=gtx&sl=auto&tl=<lang>&dt=t&q=` endpoint, no key, best effort; deepl = `api-free.deepl.com/v2/translate` with `[Translate] DeepLKey` typed by the user), `TargetLang=ja` (host's language), `ShowOnHost=true`, `BroadcastToAll=false` (send "(訳) text" to everyone via Chat.All, paced), `TranslateForPlayers=true` (translate Japanese chat from anyone into each foreign player's `/lang` language and send it privately, only for players who chose a non-ja language), `MinChars=3`, `MaxPerMinute=20` (global cap; drop beyond), `SkipCommands=true`.
* Flow: `ChatController.AddChat` postfix (host, incoming from others and own outgoing): if enabled and the text is not a command → enqueue `TranslateJob(text, sourcePlayerId)`; a background `Task` (System.Net.Http.HttpClient, 5 s timeout, User-Agent set) calls the provider; the result is handed back through a thread-safe queue drained by `Scheduler.Tick` (main thread). Detected source language comes from the provider (google returns it in `[2]`); if it equals the target language → no output. Output on the host: `Chat.Local("訳", "<name>: <translation>")`; to all: `Chat.All("訳", …)` when BroadcastToAll; private translations for foreign players when TranslateForPlayers. Cache identical texts for 10 minutes.
* Privacy/README: chat text is sent to Google/DeepL; document it; off by default until the user enables it in the gear panel / settings tab (descriptor rows: Enabled, Provider, BroadcastToAll, TranslateForPlayers).
* Never translate `/` commands or messages that are only emoji/digits; never block the chat pipeline (all async).
* Welcome notice when translation is enabled: one line "🌐 翻訳あり: 外国語で書いても自動で翻訳されます / Auto-translation is on / 自动翻译已开启" (short, ≤100 chars) appended to the welcome; `/h` lists `/lang` and the translation note.
* Language auto-detect (user request): when a player who has not chosen `/lang` writes a message and the provider detects `zh`/`en` (confidence ok, ≥ 6 chars), call `Lang.SetPlayerLang(id, detected)` once and send a one-line private notice in that language ("表示言語を中国語にしました。/cmd lang ja で戻せます"). Welcome message before any chat: send the notice line in the lobby language plus one compact trilingual line: "English: /cmd lang en ｜ 中文: /cmd lang zh ｜ 日本語: /cmd lang ja" so foreign players can switch immediately; if `[Chat] WelcomeAllLanguages=true` send the full welcome in ja, zh and en (paced).

## I. Feedback pipeline (owner: orchestrator — launcher/scripts, not C#)
* Launcher button "不具合報告 zip を作る": collects `BepInEx/LogOutput.log` (+ the previous one if kept), `BepInEx/config/jp.pocketroles.mod.cfg`, `BepInEx/PocketRoles/lang/*.json` hashes, mod version, game version, OS version, a `report.txt` the user fills in (what happened / when / room code / players count) into `Desktop\PocketRoles-report-YYYYMMDD-HHMM.zip`. * Where to send: (1) GitHub Issue (drag & drop the zip) for people with an account — Issue templates (bug / request) in `.github/ISSUE_TEMPLATE/` ja+zh+en; (2) **e-mail to a dedicated report mailbox** (DECIDED: `pocketroles.report@gmail.com` (bugs) and `pocketroles.report+request@gmail.com` (feature requests, same inbox)): the launcher's report button also opens the default mail app with `mailto:<ReportMail>?subject=PocketRoles report <version>` so the friend only attaches the zip. `[Launcher] ReportMail` lives in `launcher-config.json` shipped in the friend zip.
* Addresses: two custom addresses on the user's Cloudflare Email Routing domain — `report@<domain>` (bugs) and `request@<domain>` (feature requests) — both forwarded to the dedicated Gmail mailbox; the fetcher sorts by recipient/subject into `reports\bugs\` and `reports\requests\`. Launcher: two buttons ("不具合を報告" / "機能の要望を送る"); each shows a dialog with the address (copy button), tries `mailto:` and offers "Gmail をブラウザで開く" (`https://mail.google.com/mail/?view=cm&to=<addr>&su=<subject>&body=<template>`) for people without a mail app; the request template asks: what feature, why, how it should behave. Manual text (ja/zh/en) states both addresses and that webmail is fine (attach the zip from the Desktop).
* `tools\ReportFetcher\` (C# net8 console, MailKit via NuGet): reads `report-mail.json` (imap host, user, app password — the USER types the password; the assistant never reads/echoes it), downloads `.zip`/`.log` attachments of unread mails into `Desktop\PocketRoles\reports\<date>-<sender-hash>\`, marks them read and moves them to an "Processed" folder; `fetch-reports.cmd` wrapper. Gmail needs 2-step verification + an app password; Outlook.com likewise. Storage stays small (zips ≈ 100 KB).
* `analyze-reports.ps1` (project root): scans `reports\*.zip` + open GitHub issues (`gh issue list --json`), extracts each log, and prints a table: report id, mod version, game version, first error/exception signature, patch failures, disconnect reasons, count per signature (clustered), so the assistant can triage dozens at once. README section 「不具合の報告方法」 in ja/zh/en.

### M-extra. Public-list visibility test (added 2026-09-07 evening, user request "バニナ部屋に表示されるように最善を尽くす")
Facts from the 2026.8.18 dump: the Find Game filter system has a `ModFilter` (`GameFilter.FILTER_TYPE_MOD`, `AcceptedValues: Guid`) that `CurrentModRegistration.UpdateFilterSetWithModRegistrationSettings` adds for GUID-registered all-client mods, and the host sends `Tags.HostModdedGame` when hosting a modded lobby. A vanilla client never adds a ModFilter, so a registered (+25) host-only lobby is expected to be excluded from the vanilla public list server-side (Help Center: "modded games are not able to be found via public lobby search").
Test (phone, after the user's approval): host with registration ON, open Find Game on the phone (same region, all filters cleared) → record whether the lobby appears; repeat with `/opt register off` (safe mode) → record. Document the result in README ("公開一覧に出るか"). No client-side workaround exists that keeps the lobby registered; the only listing path is registration off (policy violation, user's decision, warned in chat by the safe-mode banner).
Legit discoverability helpers to consider (v0.4c): `/announce` copies "PocketRoles 部屋: CODE (Asia)" to the clipboard and can post it to a Discord webhook from the config; QR of the code in the lobby chat is not possible (text only).
