# リリースのファイルに署名する（手順）

PocketRoles のリリースには、これから **4 つ**のファイルを添付します。

| ファイル | 中身 |
|---|---|
| `PocketRoles-<版>.zip` | MOD 本体 |
| `PocketRoles-Setup-<版>.zip` | 友達用ランチャー |
| `SHA256SUMS.txt` | 上の 2 つの「指紋」（SHA-256）を書いた一覧 |
| `SHA256SUMS.txt.sig` | その一覧への、あなたの署名（**v0.5.5 から。これが新しい分**） |

`build-release.ps1` が 4 つとも作ります。作るのはいつもの 1 コマンドのままで、
**途中で鍵のパスワードを 1 回聞かれる**のだけが増えます。

---

## 1. なぜ署名するのか

Client は、GitHub から `PocketRoles-<版>.zip` を取ってきて、中の `PocketRoles.dll` をゲームに入れます。
その DLL はゲームの中で**プログラムとして動きます**。

- GitHub は、添付ファイルごとに SHA-256 を自分で計算して見せてくれます。
- `SHA256SUMS.txt` も、同じリリースの中に置いてあります。

この 2 つは「通信が途中で切れた」「ファイルが壊れた」を見つけるには十分です。
ですが、**リリースの zip を差し替えられる立場の人**（GitHub のアカウントを乗っ取った人など）は、
その 2 つも一緒に書き換えられます。どちらもリリースの中にあるからです。

署名の鍵だけは違います。鍵はこの PC（と USB の控え）にしかなく、パスワードで守ってあります。
Client の中には**公開鍵だけ**が入っています。
ですから「あなたの鍵で署名された一覧」と合う zip だけを入れる形に**したら**、
リリースを差し替えられても、Client は入れなくなります。

> **まだ「したら」の話です。** この文書でできるのは、署名を**作る**ところまでです。
> 署名を**確かめる**側は、まだどこにも入っていません。
> Client に `support\CLIENT-SUMS-VERIFY-SPEC.md` のとおりに入れて、はじめて効きます。
> いま友達に配っているランチャー（`PocketRolesLauncher.ps1`）も、`SHA256SUMS.txt` を読みません。
> 今どこまで効いているかは 7 章にまとめてあります。

使う鍵は、Aegis の定義ファイル（`aegis\definitions.txt`）に署名しているのと**同じ鍵**です。
新しく作るものはありません。

---

## 2. 手順（ふだんのリリース）

0. **先に、定義ファイルの署名が有効になっていることを確かめます。**
   デスクトップの「PocketRoles 署名の鍵」フォルダーの `定義ファイルに署名する.cmd` を実行します。
   `build-release.ps1` は、いちばん最初に定義ファイルの署名を確かめ、合わなければ**そこで止まります**。
   止まったときは、zip も一覧も 1 つもできていません。

1. **いつもどおりビルドします。**

   ```
   powershell -NoProfile -ExecutionPolicy Bypass -File build-release.ps1
   ```

2. **途中で「パスワード」と聞かれます。**
   「PocketRoles 署名の鍵」フォルダーの `定義ファイルに署名する.cmd` で入れているのと同じパスワードです。
   USB の控えを挿しているときは、どちらの鍵を使うかも聞かれます（番号を選びます）。

3. **緑色で「署名しました」と出れば終わりです。**
   `dist` フォルダーに 4 つのファイルができています。

4. **GitHub のリリースに 4 つとも添付します。**
   `SHA256SUMS.txt.sig` を入れ忘れないでください（入れ忘れると、新しい Client がインストールを止めます）。

### うまくいかないとき

| 出てきた文 | どうするか |
|---|---|
| `aegis\definitions.txt の署名が合いません` | デスクトップの「PocketRoles 署名の鍵」の `定義ファイルに署名する.cmd` で署名し直してから、もう一度ビルドします（この時点では zip はまだ 1 つもできていません） |
| `「PocketRoles-<版>.zip」の中身が一覧と違います` | `build-release.ps1` をもう一度最初から実行してください（zip を作り直したあとの古い一覧が残っています） |
| `署名の鍵が見つかりません` | USB の控えを使うなら、挿してからもう一度。PC の鍵は「PocketRoles 署名の鍵」フォルダーにあります |
| `この鍵は無効にしてあります` / `信頼する鍵の一覧に入っていません` | 新しい鍵で署名しようとしています。先に公開鍵を MOD とトレイアプリと Client に入れて出してください |
| `dist\SHA256SUMS.txt に署名できませんでした` | 署名しないまま公開しないでください。パスワードを入れ直して、下の「あとから署名する」を実行します |
| `release=<版> はもう別の中身で署名しています` | その版は前にも署名しています。**まだ 1 度も公開していない**なら、鍵のフォルダーの `signed-releases.txt` のその 1 行を消してから、もう一度。**公開したあと**なら、版を上げてビルドし直してください（4 章） |

### あとから署名する

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\sign-definitions.ps1 -SignRelease "dist\SHA256SUMS.txt"
```

### 署名できているか確かめるだけ（パスワードは要りません）

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools\sign-definitions.ps1 -VerifyRelease "dist\SHA256SUMS.txt"
```

### パスワードを入れずにビルドしたいとき（試しに作るだけのとき）

```
powershell -NoProfile -ExecutionPolicy Bypass -File build-release.ps1 -NoSign
```

**この `dist` は公開できません。** 署名がないので、新しい Client はインストールを止めます。

---

## 3. かかる時間

パスワードを 1 回打つだけです。**1 リリースあたり 1 分もかかりません。**
添付するファイルが 3 つから 4 つに増えます。

---

## 4. `SHA256SUMS.txt` の中身

```
# PocketRoles のリリースに添付するファイルの SHA-256
# format=PocketRoles.Release.Sums.v1
# release=0.5.5
# built=2026-09-23T04:00:00Z
9cd8…83  PocketRoles-0.5.5.zip
4445…85  PocketRoles-Setup-0.5.5.zip
```

- `#` で始まる行は、ふつうのチェックサムの道具では読み飛ばされます。
  ただし**署名は、この行も含めたファイル全体にかかっています**。
- `# release=` の版は、Client が「今インストールしようとしているリリース」と同じかを確かめます。
  古いリリースの署名済みの一覧を持ってきて使い回す、ということができなくなります。
- 署名する前に、`build-release.ps1` は**一覧に書いた zip をもう一度読み直して**、
  指紋が同じかを確かめます。作り直したあとの古い一覧に署名することはできません。
- **同じ版で作り直して署名し直せるのは、その版をまだ 1 度も公開していないときだけです。**
  署名した版は、鍵のフォルダーの `signed-releases.txt`（台帳）に 1 行ずつ残ります。
  同じ `release=` を**別の中身**で署名しようとすると断ります。
  （同じ版の署名済みの組が 2 つあると、先に公開した組をそのまま置き直すだけで、
  署名も `release=` も通ったまま古いビルドを配れてしまうためです。定義ファイルの
  `signed-versions.txt` とまったく同じ考え方です。）
  まだ公開していないなら、台帳のその 1 行を消せば署名し直せます。公開したあとなら、版を上げてください。

---

## 5. 署名の中身（`SHA256SUMS.txt.sig`）

定義ファイルの `.sig` とまったく同じ形です。

```
<署名の base64>
keyid=91400fdf0f5af4ca
```

- RSA 3072 / SHA-256 / PKCS#1 v1.5
- 署名するのは「先頭の BOM を取り除き、改行を LF にそろえた」ファイルの中身です
  （GitHub の raw は LF、Windows の作業コピーは CRLF なので、どちらでも同じ署名で通ります）。

---

## 6. 定義ファイルの署名とは混ざりません

同じ鍵を使いますが、2 つのファイルを取り違えることはできません。

- `SHA256SUMS.txt` には `version=` の行がありません。MOD もトレイアプリも、
  `version=` のない定義ファイルは使いません。
- `aegis\definitions.txt` には `# format=PocketRoles.Release.Sums.v1` の行がありません。
  `-SignRelease` と `-VerifyRelease` は、その行のないファイルを断ります。
- `-Sign`（定義ファイル）と `-SignRelease`（リリースの一覧）は、
  それぞれ相手のファイルを断ります。

---

## 7. これで防げること・防げないこと

### 今どこまで効いているか（先に読んでください）

- **MOD の zip（`PocketRoles-<版>.zip`）＝まだ誰も確かめていません。**
  署名は作りますが、入れる側（ランチャー・Client）が読んでいません。
- **ランチャーの zip（`PocketRoles-Setup-<版>.zip`）＝これからも確かめません。**
  `CLIENT-SUMS-VERIFY-SPEC.md` 1 章 B の 3 は `PocketRoles-<版>.zip` の行しか探さない決まりです。
  ランチャーは信頼する鍵の一覧と定義ファイルを運ぶ出発点なので、ここは別に考える必要があります。
- **Aegis の定義ファイル（`aegis\definitions.txt`）＝署名済みで、MOD もトレイアプリも確かめています。**
  今ちゃんと効いているのはここだけです。

### 表

「署名の後」は、**`CLIENT-SUMS-VERIFY-SPEC.md` を Client に入れたあと**の話です。

| こわいこと | 署名の前 | 署名の後 |
|---|---|---|
| 通信が途中で切れる／ファイルが壊れる | GitHub の digest で分かる | 同じ |
| GitHub のアカウントが乗っ取られて zip を差し替えられる | **防げない**（一覧も digest も一緒に直せる） | **まだ防げません**。署名は作っていますが、確かめる側が未実装です。ランチャーは確かめません。Client に `CLIENT-SUMS-VERIFY-SPEC.md` の B を入れてから「防げる」になります |
| リリースのページだけをまねた偽サイトに誘導される | 防げない | 同じ（Client は GitHub の決まった場所しか見ません） |
| 古いリリースの署名済みファイルを使い回される | — | `# release=` が今のリリースの版と違うので入れません（B を入れたあと） |
| 同じ版で作り直した、別の中身の署名済みファイルを置き直される | — | `KeyDir\signed-releases.txt` の台帳が、同じ `release=` に別の中身で署名することを断ります（4 章） |
| 鍵そのものを盗まれる | — | **防げません**。鍵は USB の控えも含めて人に渡さないでください |

## 8. 関連するファイル

| ファイル | 中身 |
|---|---|
| `build-release.ps1` | 4 つのファイルを作り、最後に署名を求めます |
| `tools\sign-definitions.ps1` | `-SignRelease` / `-VerifyRelease`。鍵とパスワードは本人に聞きます |
| 鍵のフォルダーの `signed-releases.txt` | 署名したリリースの台帳（秘密ではありません）。「1 つの版に 1 つの中身」を守ります（4 章） |
| `support\CLIENT-SUMS-VERIFY-SPEC.md` | Client 側で署名をどう確かめるか（実装の仕様） |
